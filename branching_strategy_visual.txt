GIT COMMANDS QUICK REFERENCE:
═════════════════════════════

    STEP 1: Create release branch for customer
    ─────────────────────────────────────────────
    $ git checkout v10.0
    $ git checkout -b release/v10.0
    $ git push origin release/v10.0

    STEP 2: Create hotfix branch
    ─────────────────────────────
    $ git checkout release/v10.0
    $ git checkout -b hotfix/customer-v10.0-fix1

    STEP 3: Make fix and push
    ──────────────────────────
    $ # Make your code changes
    $ git add .
    $ git commit -m "Fix: [Description]"
    $ git push origin hotfix/customer-v10.0-fix1

    STEP 4: Create Merge Request in GitLab UI
    ──────────────────────────────────────────
    Source: hotfix/customer-v10.0-fix1
    Target: release/v10.0

    STEP 5: After merge, tag and deploy
    ────────────────────────────────────
    $ git checkout release/v10.0
    $ git pull
    $ git tag -a v10.0.1 -m "Hotfix for customer"
    $ git push origin v10.0.1
    $ # Deploy v10.0.1 to customer


ADVANTAGES:
═══════════

    ✓ Customer stays on stable v10.0 (no unwanted features)
    ✓ Hotfixes are isolated and tested
    ✓ Main branch continues with new development
    ✓ Can support multiple customers on different versions
    ✓ Clear audit trail and version history
    ✓ Minimal risk of introducing new bugs
    ✓ Easy rollback if needed


KEY POINTS:
═══════════

    1. Main branch = Ongoing development (v11.0, v12.0, etc.)
    2. release/v10.0 = Frozen version for customer
    3. hotfix/* branches = Individual fixes
    4. v10.0.1, v10.0.2 = Patch versions (hotfixes)
    5. Customer gets only the fixes they need
    6. No forced upgrades
